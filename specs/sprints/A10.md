# Sprint A10 — Form & Meta lead intake

> **Status:** IMPLEMENTED (awaiting review) · spec v1 · 2026-10-19 — see **As built** at the end
> **Parent docs:** [`SCOPE-GAP-PLAN.md`](SCOPE-GAP-PLAN.md) (gap 1; decisions D1 both/email first, D2 Google
> Workspace, D3) · final scope §5A, §8, §14 #1 · [`A4.md`](A4.md) (widget leads) · ADR-003 (inbound email)
> **Outcome:** a landing-page form submission, a Meta lead notification e-mail forwarded from the REBECCA Gmail
> inbox, or a Meta Lead Ads webhook becomes **one** lead with its source and permission evidence, and the agents
> follow up automatically — no one forwards anything by hand. Duplicates never create a second lead or a second
> plan; anything unreadable lands in an **intake queue** for a person, never guessed.

## Decisions

| # | Decision | Why |
|---|---|---|
| I1 | One intake pipeline for every source (`web_form`, `meta_email`, `meta_api`): normalise fields → validate (the A5 row rules) → **record an intake event keyed by (source, external id)** → create the lead → the **same post-capture steps as a widget lead** (assignment, "new lead" notification, CRM sync, email check, agents hook). The post-capture steps are moved out of the widget route into one shared function | One behaviour for every lead; nothing duplicated |
| I2 | **Idempotent per source id**: form `submission_id` (else a hash of the submitted fields), the notification e-mail's `Message-ID`, Meta's `leadgen_id`. A repeat is recorded as `duplicate` and does nothing. A *different* submission from a known person reuses their contact; the one-active-plan rule prevents a second plan | Scope §14 "duplicated form notifications" |
| I3 | **Permission (D3)**: submitting the form is **email** permission (`express_consent`, source `form`/`meta`, the tenant's configured form wording as evidence). **AI calls** only when the submission carries a call-consent answer = yes **and** the tenant has saved the exact call-consent wording its form shows (`express_written_consent` + that wording). A phone number alone never makes a lead callable | Scope §5A.4, §10 |
| I4 | **Timezone**: the form's `timezone` field if present; otherwise inferred from a US phone number only when its area code maps to **one** zone (`phonenumbers` library, kept inside the intake module). Ambiguous / unknown → no timezone → calls stay blocked (`CONTACT_TIMEZONE_UNKNOWN`), email still goes | Calling hours are the called party's local time; never guess across zones |
| I5 | **Landing-page forms**: `POST /public/intake/forms/{token}` (JSON or form-encoded). The URL token (HMAC, purpose `intake.form.v1`, per tenant) is the credential — meant for server-side posting (form tool / Zapier webhook). Field names follow the CSV aliases plus `submission_id`, `form`, `campaign`, `call_consent` | Same pattern as Inbound Parse |
| I6 | **Meta notification e-mails (D1 first, D2)**: the REBECCA Gmail inbox auto-forwards Meta lead notifications to a per-tenant intake address handled by SendGrid Inbound Parse → `POST /public/intake/email/{token}`. Accepted only when the original sender's domain is in the tenant's **trusted senders** (default `facebookmail.com`) **and** its DKIM passed. A generic `Label: value` parser reads the fields (HTML is flattened first); unknown labels are kept as the lead's form answers. **Gmail's forwarding-confirmation e-mail** is detected and its confirmation code shown to the admin (Gmail requires confirming the forwarding address) | Works today without Meta app review |
| I7 | **Meta Lead Ads API (D1 second)**: `GET /public/intake/meta` answers Meta's subscription challenge (`META_VERIFY_TOKEN`); `POST` verifies `X-Hub-Signature-256` with `META_APP_SECRET`, maps `page_id` → tenant (a page belongs to one tenant) and **queues** an outbox event; the dispatcher fetches the lead from the Graph API with the tenant's encrypted page token and ingests it (retries + dead-letter for free). Both platform settings unset → the endpoint answers 404 | Meta wants a fast 200; fetches can fail and must retry |
| I8 | **Intake queue**: rejected (missing/invalid contact details, untrusted sender, unparseable), and notices (Gmail confirmation code) — admin list with the reason, the parsed fields (no raw bodies kept), and **Resolve**. Accepted / duplicate events are kept as the audit of what arrived | Scope §9 "error queue … do not guess" |
| I9 | Admin: `GET/PUT /admin/intake/config` (enabled, trusted senders, form consent wording, call-consent wording, Meta page id + page token write-only) returning the form URL and the e-mail intake URL; `GET /admin/intake/events`, `POST /admin/intake/events/{id}:resolve`. CLIENT_ADMIN (PLATFORM_ADMIN via the tenant route). Console page **Outreach → Lead intake** | Same RBAC as other outreach settings |

## Data (migration 0074)
`tenant_lead_intake_configs`, `lead_intake_events` (unique `(tenant_id, source, external_id)`),
`meta_page_routes(page_id PK, tenant_id)`; `contact_consents.source` also allows `form`, `meta`.

## Tests
Parser units (labels, HTML, line-split values, aliases, Gmail confirmation, consent answers, timezone
inference incl. ambiguous). Integration (real DB, signed requests): form → lead + contact + consents + plan +
lead notification; the same submission twice → one lead; a known person's second form → same contact, no second
plan; no call consent / no wording → email only; untrusted sender and missing contact details → queue; Gmail
confirmation → notice with the code; Meta webhook: bad signature 401, challenge, unknown page ignored, fetch
retried after a Graph failure then ingested; tenant B's token never writes into tenant A; RBAC on config/queue.
