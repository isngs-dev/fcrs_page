> **Outcome:** the agentic layer is proven end to end, holds under hostile input and concurrent load, fails
> **explicitly** (and retries) when a dependency breaks, and meets the two compliance items left for A9
> (recording retention, a contact's export / erasure). Operators get a runbook.

## Decisions

| # | Decision | Why |
|---|---|---|
| H1 | **E2E inbound journey** on a real DB, driven only through HTTP endpoints, the outbox and the task dispatcher (no internal shortcuts): widget lead with email consent → plan → follow-up email → the person replies proposing a time → booked → plan stopped | PHASE0 §6 A9 |
| H2 | **E2E outbound journey**: CSV import with call consent → commit → dispatcher places the call → signed Plivo webhooks (disclosure, Q&A, slot offer, "yes") → booked → hangup settles the task → confirmation email → plan stopped | PHASE0 §6 A9 |
| H3 | **Prompt-injection set** with a *fooled model*: only the LLM provider and retrieval are faked, and the fake obeys the attacker. The real classify / compose / answer / voice code and its guards must still keep behaviour safe: mail only to the thread's contact, no extra plans, no suppression of anyone but the sender, no unsupported prices / discounts / promises spoken or sent, no instruction leak, no "I'm a human", transfers only to the configured number | email_agent §4, calling_agent §8 — "even if the model is fooled" is the real bar |
| H4 | Call replies get the same **unstated-commitment** check as emails (amounts, percentages, "free/discount/guarantee/refund/…" not in the retrieved context → no answer, `voice_agent_miss` logged with the reason). The check moves to `orchestrator/guardrails.py` so email and voice share one implementation | Gap found while specifying H3: a fooled model could have *said* "90% off" on a call |
| H5 | **Concurrent-call cap is atomic**: the call session is created under a per-tenant transaction lock that re-counts live calls; over the cap → the task is deferred (no attempt used), same as the gate's `CALL_CONCURRENCY_LIMIT` | The A6 cap was check-then-act across two steps; parallel dispatchers could exceed it |
| H6 | **Load test** (integration, `-m integration`): 30 due call tasks, cap 5, 4 dispatchers in parallel → exactly 5 calls placed, 25 deferred, no task claimed twice; then 5 live calls × 6 turns of signed webhooks in parallel → every turn answered, our own handling time (model faked at 0 ms) reported as p50/p95 | calling_agent §8 |
| H7 | **Failure drills** — each dependency broken in turn; each must fail *explicitly* (a recorded status/error code, nothing fabricated) and recover by retry: SendGrid 5xx (retry, one email, same Message-ID) and 4xx (failed, not retried); model down while composing (task retried, no email invented); Plivo 5xx / 4xx on dialling; model down mid-call (caller hears the team hand-off, needs-human event); outbox handler crash (backoff → dead-letter after 5); a worker dying mid-task (reaper returns it, runs once); duplicate webhook deliveries (processed once); kill switch flipped mid-flight | PHASE0 "all drills fail explicitly + retry" |
| H8 | **Recording retention** (compliance §5): `tenant_call_agent_configs.recording_retention_days` (default 90, 1–3650). A daily Beat task deletes recordings older than that at Plivo and clears the URL; transcripts stay with the contact. A Plivo error leaves the row for the next run (logged), never a silent skip | Compliance §5 |
| H9 | **A contact's agent data — export and erase** (compliance §6), CLIENT_ADMIN only, audited: `GET /admin/outreach/contacts/{id}/agent-data` (JSON: plans + tasks, consents, suppressions matching them, email threads + messages, calls + transcripts) and `DELETE` of the same (deletes plans/tasks, threads/messages, calls/transcripts, and the recordings at Plivo first; **keeps consents and suppressions** as proof / blocklist). A Plivo failure aborts before any row is deleted | Compliance §6 |
| H10 | **Runbook** `specs/runbook.md`: turning agents on for a client, both kill switches, what each Beat job does, the drills table (symptom → what the system does → what the operator does), alerts/log events to watch, DSR + retention, and the go-live checklist. `deploy/.env.example` re-checked against `config.py` | PHASE0 §6 A9 |

## As built (2026-10-19)

Four real defects were found by the new tests and fixed (each test was seen failing first):

| # | Found by | Defect → fix |
|---|---|---|
| O1 | Load test (H6) | **The call cap could be exceeded**: 4 parallel dispatchers placed **6 calls with a cap of 5**. The session insert now re-counts live calls under a per-tenant transaction lock (`call_agent/repository.create_session(limit=…)`); over the cap the executor raises `DeferTask` and the dispatcher reschedules without using an attempt. Repeated runs: exactly 5 placed, 25 deferred, 0 attempts used |
| O2 | Injection set (H3/H4) | **A fooled model's price/promise would have been spoken on a call** ("90% off", "guaranteed… free gutters", "$4,500 all in"). `unstated_commitments` moved to `orchestrator/guardrails.py` and now also runs on every spoken answer; the miss is logged (`voice_agent_miss`, reason `unstated commitment`) and the caller hears the team offer |
| O3 | Failure drills (H7) | **A model outage permanently failed follow-up emails** — `LLMError` is an `AppException` (502), and the dispatcher treated every `AppException` as final. Now an `AppException` with a 5xx status is retried with backoff (its code recorded) and fails only after `max_attempts`; 4xx stays final |
| O4 | E2E journey H2 | **Dropped plan steps left dead time**: a call-only client's first call waited 2 days (the email step in front of it was dropped), an email-only plan's second email came after 4 days instead of 2. A dropped step now gives its slot back: kept steps keep the 2-day rhythm and the first starts when the plan starts (gap + calling-window rules still apply afterwards; the 400-plan property test still holds) |

| # | Note |
