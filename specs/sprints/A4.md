# Sprint A4 — Inbound automation (widget consent checkboxes → automatic follow-up)

> **Status:** IMPLEMENTED (awaiting review) · spec v1 · 2026-10-15 — see **As built** at the end
> **Parent docs:** [`../PHASE0_PLAN.md`](../PHASE0_PLAN.md) C8 + A4 row · [`../compliance.md`](../compliance.md) §1–2 ·
> [`A1.md`](A1.md) (planner, gate) · [`A2.md`](A2.md) (composer)
> **Skills:** `guardrails`, `platform-foundations`, `chat-widget`, `lead-capture-crm`.
> **Outcome:** a visitor who leaves their details in the widget can tick *"Email me about my enquiry"*
> and (when the tenant uses calls, with a phone number) *"OK to call me, including an AI assistant"*.
> The exact wording shown is stored per channel. If the tenant has inbound automation on, an
> `inbound_auto` plan starts (email ≈ 5 min later; call only with call consent, timezone and window).
> The first email refers to what they asked in the chat.

## Decisions

| # | Decision | Why |
|---|---|---|
| H1 | **Per-channel, optional checkboxes** next to the existing required storage consent, in the **LeadForm** (email + call) and the **IdentityForm** (email; it has no phone). The booking form is excluded: a booking stops the plan anyway | PHASE0 C8 |
| H2 | **Server-owned wording, versioned.** The widget sends `channel_consents: {email, call, version}`; the server stores the canonical text for that version (`api/agents/consent_wording.py`). Unknown version → 422 `CONSENT_VERSION_UNKNOWN`. Call consent without a phone → 422 `CALL_CONSENT_NEEDS_PHONE` | What's stored is exactly what that widget build showed; the client can't inject wording |
| H3 | Bases: email box → `express_consent` (source `widget`); call box → `express_written_consent` (source `widget`; checkbox + stored wording + timestamp = e-sign record). Evidence: `lead_id`, `visitor_id`, wording version, capture time, origin-free | compliance §2, A1 D5 |
| H4 | **Tenant opt-in:** new `agent_settings.inbound_auto_enabled` (default **false**). Session admission returns `outreach_consent: {email, call, version}` only when it's on, `email` ∈ channels for the email box, `call` ∈ channels for the call box → the widget shows exactly the boxes that can be used | No consent asked for a channel that can't be used |
| H5 | **Lead → contact for outreach:** when a lead arrives with ≥ 1 channel box ticked and automation on, the handler creates (or reuses) a **contact linked to the lead** (`contacts.lead_id`), owner = the lead's assigned agent, identities email/phone/visitor_id, timezone from the browser. The lead is **not** marked converted; the existing "convert to contact" action reuses this linked contact instead of failing | Plans run on contacts (A1); converting is still a human sales decision |
| H6 | Trigger: outbox kind **`inbound_lead_created`** (enabled now) emitted right after the lead write with `{lead_id, consents, timezone, captured_at}`. The lead routes don't run in a transaction, so this emit is post-commit and fail-safe (logged, never fails the capture) — same as A2 E10 | Extend, don't rewrite the capture routes |
| H7 | Handler: contact (H5) → consent rows (H3) → `planner.create_plan(kind="inbound_auto")`. `PLAN_ALREADY_ACTIVE` → done (one plan per contact). No consent ticked → nothing | A1 planner + policy decide channels/timing |
| H8 | **Composer context:** when the conversation has no rolling summary yet, the last 3 visitor messages (quoted, as data) are used so the first email can refer to their question | PHASE0 A4 demo criterion |
| H9 | Browser timezone (`Intl…timeZone`) is the contact's timezone for calling windows; invalid → not set (calls then drop with `CONTACT_TIMEZONE_UNKNOWN`) | compliance "contact-local window" |

## Changes
- Migration **0069**: `agent_settings.inbound_auto_enabled boolean NOT NULL DEFAULT false`.
- API: `PUT /admin/outreach/settings` accepts `inbound_auto_enabled`; session admission adds `outreach_consent`.
- `POST /public/leads` and `POST /public/chat/identity` accept optional `channel_consents` and `timezone`.
- Widget: `ChannelConsents` checkboxes (unticked by default, own labels, keyboard/ARIA), wording constants
  mirrored from the server registry (`version: "2026-10-a"`), payload fields; session flag plumbing.

## Tests
Unit (API): wording registry + validation (unknown version, call without phone, identity form call → 422).
Integration (real DB): lead with email+call consent → contact linked to lead, 2 consent rows with the
canonical wording, timezone set, plan created with email +5 min and call (window-shifted); automation off
→ nothing; no boxes → nothing; second lead from same visitor → no second plan; convert-to-contact
reuses the linked contact; tenant isolation of the handler; session admission flags. Widget (vitest):
boxes shown per flags, unticked default, payload carries `channel_consents` + `version` + `timezone`,
nothing sent when no box shown.

## Out of scope
SMS consent (no SMS channel yet), per-tenant wording customisation, consent withdrawal UI in the widget
(opt-out = unsubscribe link / "stop" on calls), admin toggle UI (A8).
